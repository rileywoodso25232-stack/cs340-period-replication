不需要重做已经解决的 Windows 修复和依赖下载。组员历史材料用于对照和方法参考，本人结果必须来自本人批次。

## 每一步先说明什么

每次开始操作前，先用通俗语言说清：

1. **现在做什么、为什么做**：这一步解决哪个复现问题。
2. **会操作哪里**：准备文件、编译、试跑、重放或统计；区分 Git 分支与 Linux 运行目录。
3. **怎样算通过**：需要看到什么日志、结果或一致性证据。
4. **发现问题怎么办**：先说明实际现象和影响，保留原始记录，再定位原因；未解释问题不直接扩大实验规模。

完成后说明实际结果、保存位置和下一步。数字与论文不一致也应保留，不能把“吻合论文”作为唯一通过条件。

## 阶段之间怎样切换分支

Git 分支是项目进度的保存线；Linux 独立目录是实际运行实验的副本，两者用途不同。
未提交的文件可能随切换分支一起移动，分支名称本身不会把这些文件保存成历史记录。

一个阶段完成后，先检查并保存该阶段的提交，再建立下一阶段分支。提交说明按课程规范包含 `1240013942 刘竞辰` 与实际工作。
新分支从包含所需成果的提交开始；若 main 已合并这些成果，可以从更新后的 main 开始。同步前检查未提交改动，网络不可用时明确记录本地基础版本。
新分支会继承此前必要文件，因此“分阶段”指新增工作和提交范围，不是把之前成果从目录中删除。

目前准备文件仍留在当前分支工作区；用户可在后续审查和阶段留痕时通过 GitHub Desktop 保存。
