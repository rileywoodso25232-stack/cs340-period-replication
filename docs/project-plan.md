## Suggested work sequence

1. Complete membership, inspect the paper, validate the Linux/Docker route.
2. Run smoke cases; record build commands, versions, failures and fixes.
3. Freeze the claims, baseline, representative subset and measurement protocol.
4. Collect at least three independent runs per setting, including failed attempts.
5. Quantify discrepancies and conduct controlled checks of explanations.
6. Run one single-factor extension; write the English report and prepare delivery.

## Assessment mapping

| Report criterion | Weight | Repository evidence |
| --- | --- | --- |
| Reproduction results | 30% | `results/raw/`, summary, Paper vs. Ours table, figures |
| Critical analysis | 30% | `docs/analysis.md`, controlled checks and claim verdicts |
| Setup | 15% | claims, upstream commit, environment records, deviations |
| Extension | 15% | `experiments/extension/`, logs and interpretation |
| Writing | 10% | `report/`, references, contributions and AI statement |

| Git-history criterion | Weight within Git assessment | Repository evidence |
| --- | --- | --- |
| Weekly commits | 30% | Actual timely pushes and substantive commits |
| Reproducibility/environment | 25% | Validated README, pinned setup, source/input scripts |
| README/code quality | 25% | Clear commands, measured runtimes, licenses and provenance |
| Individual contributions | 10% | Four independent accounts and substantive work |
| Repository management | 10% | Descriptive identity-bearing commits, ignore rules, final tag |

The report, presentation and Git assessment each have their own grading. Their
relative course weights are not given in the supplied document.
