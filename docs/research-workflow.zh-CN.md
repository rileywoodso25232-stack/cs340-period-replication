# PERIOD 复现与拓展：分阶段工作流

更新：2026-10-27。面向首次做科研的小组成员。
本文是执行计划，不是实验完成记录；具体命令、用例和参数在对应阶段验证后确定。

## 如何使用

每轮对话集中完成一个阶段：先说明当前状态，再执行该阶段的工作，保存证据，最后检查通过条件。
未通过时优先解决当前问题，不要直接扩大实验规模。阶段完成不一定需要结果与论文完全一致；
真实且可解释的失败也可以进入后续分析，但工具本身尚不能可靠运行时不能开始正式测量。

总体顺序：选择实验机器 → 固定源码与环境 → 编译 → 安装验证与重放 → 固定研究问题与用例
→ 小批量预实验 → 正式复现 → 统计对比 → 差异验证 → 拓展设计与执行 → 整理交付。

老师要求核对依据：课程说明第 2–4 页。论文依据：PERIOD 表 1–2、§4.1–4.5。
报告的复现结果与关键分析各占 30%，拓展占 15%；允许说明范围后缩小规模。
每项主张应对应原论文图表，至少三次运行，报告均值和标准差，每个数值可追溯至日志。

## 阶段 1：选择一台可长期使用的实验机器

**做什么**

1. 盘点小组可用的电脑、Linux 机器或虚拟机，记录 CPU、内存、磁盘、系统和管理员权限。
2. 选择主要实验机器，正式对比尽量固定在同一台机器上执行。
3. 核对上游对 Linux 内核和调度权限的要求。PERIOD 使用 SCHED_DEADLINE，
   因此“能启动 Ubuntu／Docker”还不等于“能运行 PERIOD”。
4. Windows 可继续用于编辑、Git 协作；WSL、Docker Desktop 或虚拟机是否适用，必须通过实际测试确认。

**怎么验证**：能进入实验系统、获取文件、使用所需权限，并记录实际内核和资源。
关键调度能力在阶段 4 通过运行日志和行为继续验证。

**留下什么**：在环境说明中记录机器选择、资源、权限及待验证事项。
**下一步条件**：确定可用机器与安装路线；若关键权限不具备，先换路线，不开始批量实验。

## 阶段 2：固定上游源码与环境版本

**做什么**

1. 使用仓库的源码获取脚本取得 config/upstream.json 指定的 PERIOD commit。
2. 阅读该版本的 INSTALL.md、REQUIREMENTS.md 和构建文件；不要混用另一个版本的教程。
3. 尽量对齐论文的 Ubuntu 18.04、GCC 7.5、LLVM 10.0。
4. 用环境采集脚本保存记录，并补全内核、容器镜像、依赖、编译参数等未自动采集的信息。
5. 无法对齐的设置逐项写入 docs/deviations.csv：原设置、实际设置、原因。
   容器不会固定宿主机内核，宿主机与容器内的信息都需要记录。

**怎么验证**：实际源码 SHA 与配置一致；工具版本来自运行输出；输入来源和获取步骤可重复。
**留下什么**：环境记录、源码版本、依赖与输入清单、偏差表。
**下一步条件**：能明确回答“在哪台机器、用哪份代码、哪套工具进行实验”。

## 阶段 3：编译工具和最小测试程序

**做什么**

1. 按固定版本的安装流程构建依赖、插桩工具和示例程序。
2. 每一步保留完整命令、工作目录、输出和失败信息。
3. 遇到错误，先确定发生在下载、依赖、编译、链接还是权限阶段，再验证一个原因。
4. 必须修改上游代码时，保存补丁并记录修改文件与理由；不要同时升级多项依赖。

**怎么验证**：构建命令成功退出，所需工具和示例产物实际存在，能够进入后续运行步骤。
仅有“文件生成了”仍不足以说明调度和缺陷检测有效。

**留下什么**：构建日志、可重做的步骤、实测耗时、补丁和修改清单。
**下一步条件**：最小示例已编译，且构建过程能够重做。失败时使用 systematic-debugging 排查。

## 阶段 4：安装验证与失败调度重放

**做什么**

1. 按 experiments/smoke/README.md 运行 doubleFree 安装示例。
2. 观察工具是否实际开始受控调度，有无权限错误、调度初始化失败或程序启动失败。
3. 保存标准输出、标准错误、退出状态和生成的调度文件。
4. 对检测到的失败进行重放，检查失败是否对应示例预期的缺陷。
5. 再选择一个正式 evaluation 用例进行验证，避免只证明安装示例可用。

**怎么验证**：能说明工具如何识别目标缺陷，并有相应诊断及重放证据。
“程序退出非零”“发生超时”“脚本打印完成”都不能单独作为检出缺陷的证据。
原作者示例中的调度数量用于核对，不是可以直接填入本组结果的数值。

**留下什么**：一组完整安装验证日志、至少一个失败调度及重放记录；不一致之处单独说明。
**下一步条件**：区分工具失败与目标程序缺陷，确认日志可解释。通过只证明环境可用，不证明论文结论。

## 阶段 5：固定研究问题、用例和基线

**做什么**

1. 固定两个候选问题：能否在规定预算内发现已知缺陷；并行 PERIOD 相比 Serial 是否减少搜索量。
2. 分别对应论文表 1 和表 2。初步规模为约两个 CVE 基准程序、六个 SCTBench 程序。
3. SCTBench 可从 reorder_3/4/5/10 及其他缺陷类型中选择；正式名单要依据源码和可行性验证确定。
4. 记录选入和排除的理由，不能因结果不好而事后删除用例。
5. 验证 Serial 的运行方式、编译与错误判定标准。Native 可以补充对照，但不能替代 Serial 来回答并行优势。
6. 若 Serial 无法验证，先调整研究范围和主张，不宣称已完成该比较。

**怎么验证**：每个问题都有原论文图表位置、可执行用例、对应基线和明确指标。
CVE 基准中的简化程序不等于完整 Linux／Firefox 产品；子集结论不推广为全基准结果。

**留下什么**：docs/claims.md 中的范围、用例清单、基线验证记录。
**下一步条件**：研究范围明确，主张与实验能力相符。

## 阶段 6：小批量预实验，验证数据收集流程

**做什么**

1. 先用一到两个用例跑完整流程：配置 → 执行 → 日志 → 数值提取 → 汇总。
2. 核对每个指标的含义：首次发现缺陷所需调度数、总调度数、触发缺陷的调度数、耗时。
3. 明确调度预算、单次程序运行超时和整轮实验时限；这三者不能混为一谈。
4. 手工核对几条日志与 CSV，确认解析没有取错字段或单位。
5. 区分完成、未检出、预算耗尽、超时、工具错误；为每次尝试保存状态记录。
6. 估计单个配置和完整批次所需时间，再固定正式配置及停止规则。

**怎么验证**：同一条观测能找到配置、源码版本、环境和日志；解析数值与日志一致。
现有 summarize.py 只负责数值的描述统计，不会自动判断检出率、超时或研究结论。
如需这些指标，应先补充结果状态记录及适配逻辑。

**留下什么**：预实验日志、验证后的解析方式、实际耗时估计、正式命名的 JSON 配置。
**下一步条件**：数据收集可靠，批次规模可执行。预实验单独标识，不悄悄混入正式结果。

注意：config/experiments.example.json 仍是旧草案，其 CPU 核数拓展和默认模式不是本指南的正式配置。
进入正式实验前，应按已验证方案创建独立配置；不能直接把示例配置当成已确认方案。

## 阶段 7：执行正式复现

**做什么**

1. 固定配置后运行；建议每配置五次独立重复，老师最低要求三次，论文为十次。
   实际采用的重复次数及与论文的差异要说明。
2. 每次从干净的程序状态和独立输出目录开始；涉及随机种子时记录种子。
3. 交错或随机安排方法的运行顺序，减少温度、后台任务及时间顺序的影响。
4. 正式测量时固定机器、输入和资源；不同时运行会相互争抢资源的其他实验批次。
5. 保留所有尝试，包括未检出、超时和工具错误。确需重跑时，保留原记录与重跑理由。

**怎么验证**：计划中的用例×方法×重复次数都有记录，各条记录均可追溯。
复制同一份日志五次不是五次独立运行；工具错误也不能伪装成正常观测。

**留下什么**：results/raw/ 中的真实观测和小型日志、逐次状态、环境及配置引用。
**下一步条件**：完整批次已记录且有效性核对完成；未完成项明确列出，不为了凑数量填值。

## 阶段 8：统计并制作 Paper vs. Ours 对比

**做什么**

1. 按用例、方法和配置分别汇总，不混合不同条件。
2. 对有效数值计算均值和样本标准差，注明实际样本数；按老师要求至少三次。
3. 未检出不是零；若首次检出指标存在未检出运行，另报成功次数／总次数，
   并明确成功运行的条件统计，不能将其冒充所有运行的平均发现时间。
4. 核对论文数值的表格行、指标、单位和预算，填入 paper_vs_ours.csv。
5. 计算绝对差异与相对差异；论文值为零或“未检出”时不强算百分比。
6. 制作带样本数和误差说明的图表，调度数量与耗时分别展示。

**怎么验证**：随机抽取表中几项数值，能够从图表反查汇总、原始数据和日志。
若论文没有提供原始重复数据或标准差，不补造它们，也不凭几个均值声称差异显著。
相同条件下多次运行结果完全一致时，标准差为零可以是真实结果，无需人为制造波动。

**留下什么**：对比表、统计脚本输出、图表和数据处理说明。
**下一步条件**：表中每个数字都有来源，缺失和失败的处理透明。
此阶段可用 statistical-analysis 辅助核对，课程要求和预先固定的统计方案优先。

## 阶段 9：对差异做控制变量验证

**做什么**

1. 挑选一到两个最重要的差异，先记录差异有多大、影响哪个研究问题。
2. 为每项差异提出具体假设，并写出“若假设成立，应观察到什么”。
3. 只改变一个因素做重跑，其余配置保持一致；为这组实验使用独立 ID。
4. 根据结果支持、否定或保留假设，不只写“可能是机器不同”。
5. 分别为各研究主张给出支持、部分支持、不支持或证据不足的判断。

**例子**：若搜索调度数接近论文而耗时更长，先检查单次调度成本和环境负载。
若调度数也不同，优先核对输入、插桩结果、搜索边界和错误判定标准。
这些是排查方向，不是未经验证的原因结论。

**怎么验证**：每项解释都有对应重跑或检查证据；没有证据的原因明确写成待验证假设。
**留下什么**：docs/analysis.md 中的“差异—假设—验证—结果—局限”记录。
**下一步条件**：主复现结果已理解到足以设计有意义的拓展，不要求所有差异都能解释完。

## 阶段 10：设计并验证拓展条件

**候选问题**：同一机器、固定核心数与程序输入时，后台 CPU 负载是否影响 PERIOD 的检出稳定性和耗时？

论文 §4.5 已比较不同核心数，因此旧草案的“2 核／4 核”不能直接作为新的拓展。
后台负载方案仍需检查论文补充材料，确认区别；它不是已经验证的创新点。

**做什么**

1. 从正式复现中选择三个可解释、具有不同特点的用例，写明选择理由。
2. 设无额外负载、中等和高负载三个等级；通过预实验确定可重复实现的具体水平。
3. 固定硬件、核心集合、输入、线程数、工具、深度、预算和超时规则。
4. 固定负载生成器版本、工作类型、进程数及 CPU 亲和性，只改变负载强度。
5. 核对实际 CPU 利用率及负载是否与实验争用同一核心集合，不能只相信负载命令的目标百分比。
6. 预先说明哪些观测支持或不支持假设，例如“耗时增加但调度数与检出比例稳定”。

**怎么验证**：实际负载档位有可观察差异且可重复；没有顺带改变核心数、程序输入等因素。
若调度机制隔离了负载，先确认实验操作实际生效，不能为得到预期结果任意改变方案。

**留下什么**：独立拓展配置、假设、控制变量表、负载验证记录。
**下一步条件**：研究问题确有区别，唯一主动变化因素明确，负载操作已验证有效。

## 阶段 11：执行拓展并解释结果

**做什么**

1. 按三个用例×三档负载×五次运行安排，初步为 45 次；预实验后可合理调整并提前说明。
2. 交错安排负载等级，等待条件稳定后测量；每次保留实际负载、日志、失败调度和状态。
3. 沿用主复现的错误判定和数值提取方式，统计检出成功次数、调度数、耗时、超时和重放情况。
4. 分别讨论搜索行为、执行开销和固定时限内的实际效果，避免把超时直接解释为缺陷或漏报。
5. 将发现联系回论文主张：在哪些额外条件下仍成立，哪些条件下存在局限。

**怎么验证**：结论能从数据和日志推出；没变化也是可以报告的结果，不能预设必须发现性能下降。
五次运行足以提供初步描述，但不足以精确证明普遍可靠性；如需更强结论，再有计划地增加样本。

**留下什么**：拓展结果表、图、解释、局限性及可重做步骤。
**下一步条件**：他人能按记录重做，且清楚知道实验能说明什么、不能说明什么。

## 收尾与贯穿全程的习惯

- 将结果整理为英文报告，包含设置、偏差、结果、关键分析、拓展、贡献与 AI 使用声明。
- 请另一位组员按 README 在干净环境重新搭建和运行主实验；修复遗漏步骤后再称为可复现。
- 每周更新真实进度，周日 23:59 前推送实质修改；每条提交写实际提交者的学号和全名。
- 四名成员使用各自账号，按环境、实验、分析、拓展组织主责并交叉检查，报告贡献对应真实提交。
- 小型原始日志入库；大型产物按课程规则存放并提供可追溯位置。不要只留下截图。
- 全部交付内容核对完成后再创建 v1.0，不在项目刚开始时打最终标签。

## 技能如何介入

| 技能 | 状态／来源 | 使用时机 |
| --- | --- | --- |
| pdf | 已有 | 查阅课程要求、核对论文图表与脚注 |
| systematic-debugging | 已安装；obra/superpowers | 编译、运行或结果异常时，先收集证据再逐个验证假设 |
| statistical-analysis | 已安装；anthropics/knowledge-work-plugins | 检查分组、异常观测、统计口径和结论边界 |
| spreadsheets / presentations | 已有 | 整理共享结果表、准备展示时按需使用 |

技能是帮助执行的流程，不是缺陷判定器，也不会替代真实实验或组员审阅。
