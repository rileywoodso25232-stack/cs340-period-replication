# 扩展实验:深度上限 `-d` 对 PERIOD 的影响

> 原计划比较不同 CPU 数量,未执行。2026-11-13 起改为本实验,原因见"动机"。

## 研究问题

改变 PERIOD 的深度上限(`run_PDS.py -d`)时,它在 CVE 程序上发现缺陷的能力和代价(调度数)如何变化?

## 动机

复现表 1 时,本组发现三处设置不一致:

1. 论文 4.1.3 节写明 CVE 上的深度上限为 5;
2. 本组用 `-d 3` 时,三个用例的数字与论文表 1 完全一致;
3. 作者在 CVE-2017-15265 的 README 中使用 `-d 2`,得到的总调度为 16,而论文表 1 为 96。

论文没有报告深度上限本身的影响。本实验检验:上限 3 和 5 是否等价,上限过低时会发生什么。这直接关系到论文的方法设计:PERIOD 用有限的周期数(深度 + 1)来控制搜索空间。

## 设计

- **唯一变量**:`-d` ∈ {1, 2, 3, 4, 5}
- **保持不变**:同一 Docker 环境(容器 `period-cs340`,镜像 `period:cb8deb9`,上游提交 `cb8deb9`);同一组程序;同一构建方式(每轮执行用例自带的 `build.sh`)
- **程序**:表 1 中的 CVE-2016-7911(NPD)、CVE-2016-9806(DF)、CVE-2017-15265(UAF),缺陷深度均为 2
- **轮次**:每个设置 3 个有效轮次;试运行阶段中止的轮次不计入,另行补跑
- **指标**:首次发现缺陷的调度号、总调度数、失败调度数(与表 1 相同),报告均值 ± 样本标准差
- **额外检查**:对结果不一致的调度,用 `run_PDS.py -r` 单独重放,并以必然出错的调度作对照

## 运行方法

在容器内:

```bash
cd /workdir/PERIOD && source tool/init_env.sh
/workdir/runs/run_depth.sh CVE-2016-7911 2016-7911
/workdir/runs/run_depth.sh CVE-2016-9806 2016-9806
/workdir/runs/run_depth.sh CVE-2017-15265 2017-15265
```

脚本见 `results/raw/ext-depth-2026-11-13/run_depth.sh`。每个程序约 1–2 分钟。输出写入 `/workdir/runs/ext-depth/<cve>/d<N>/`,已存在的轮次会跳过,不覆盖。补跑和重放为手动执行,命令同脚本。

## 数据与结果

- 原始记录:`results/raw/ext-depth-2026-11-13/`
- 汇总表:`results/raw/ext-depth-2026-11-13/SUMMARY.md`

## 结果要点与解释

1. **上限低于缺陷深度时找不到缺陷**:`-d 1` 时三个缺陷均未发现。
2. **首次发现位置不随上限变化**:PERIOD 按深度 1、2、3……逐层搜索,只要上限不低于缺陷深度,缺陷都在同一个调度被首次发现。
3. **搜索空间在 `-d 3` 饱和**:`-d 4`、`-d 5` 不再产生新调度(总调度 19 / 42 / 96)。因此对这三个程序,论文的上限 5 与表 1 数字一致;作者 README 中 CVE-2017-15265 的 `-d 2` 偏低,只覆盖 16 个调度。
4. **与论文主张的关系**:结果支持"有限周期即可发现浅层缺陷"的设计。对这类线程少、关键点少的程序,把上限设得比需要的大,不会增加代价。
5. **意外发现**:CVE-2017-15265 有两轮在额外调度上报出 use-after-free,同一线程顺序在其他轮次不报错,单独重放 10 次均未复现。说明 PERIOD 在该程序上的检测结果并非每次完全相同。原因未确定。

## 局限

- 只有 3 个程序,都是 2 线程、缺陷深度 2;结论不能推广到线程更多或缺陷更深的程序(如 SCTBench)。
- 只在本组 Docker 环境中运行,未在其他机器上重复。
- 耗时未作比较:每轮均重新编译,且试运行阶段不受控制。
