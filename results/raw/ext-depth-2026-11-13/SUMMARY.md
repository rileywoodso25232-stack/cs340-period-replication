# 扩展实验汇总:深度上限 `-d` 对 PERIOD 的影响

- 日期:2026-11-13;执行人:吴明阳(1240014957)
- 环境:Docker 容器 `period-cs340`(镜像 `period:cb8deb9`,Ubuntu 18.04.6,内核 6.18.33.2-microsoft-standard-WSL2,Clang 10.0.0),上游提交 `cb8deb9`
- 唯一变量:`run_PDS.py` 的 `-d`,取 1–5;程序、环境、构建方式不变;每组 3 个有效轮次
- 数据来源:各 CVE 目录下 `summary.txt` 与 `dN/runK.log`、`dN/runK-out/Errors/`;脚本 `run_depth.sh`;补跑和重放为手动执行,命令同脚本
- 指标:首次发现 = `Errors/` 中第一个文件名的调度号;总调度 = 日志 `Round` 行;失败调度 = `Total Error Interleavings`
- 统计:均值 ± 样本标准差(n = 3);耗时不作比较
- 结论范围:仅限这三个 CVE 和本组环境

| 轮次 | 额外报错 | 同一调度在其他轮次 | 单独重放 |

| `d2/run4` | 第 9 个调度报 heap-use-after-free | 线程顺序相同(对比 `d2/run1`),未报错 | 10 次均未复现(`d2/replay9-*.log`) |

这两轮正常完成,因此计入统计,导致上表中两组的标准差不为 0。

## 4. 观察

1. `-d` 低于缺陷深度时(`-d 1`),三个缺陷均未被发现。
2. 只要 `-d` 不低于缺陷深度,首次发现的调度号不随 `-d` 变化(15265 `d2/run4` 的额外报错除外)。日志显示 PERIOD 按深度 1、2、3……逐层搜索。
3. 从 `-d 3` 起,三个用例的总调度不再增加:`-d 4`、`-d 5` 虽搜到对应深度,但没有新的调度。因此对这三个用例,论文正文所述的 CVE 深度上限 5 与表 1 数字一致;作者 README 中 CVE-2017-15265 使用的 `-d 2` 只覆盖 16 个调度。
4. CVE-2017-15265 上出现两次不可复现的额外报错,同一线程顺序在不同轮次结果不同。原因尚未确定;可能与关键点之间未受控制的执行有关,这只是推测。
5. 试运行阶段不受控制,2/48 次因程序碰巧崩溃而中止整次搜索。
